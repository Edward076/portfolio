# Methodology

## Dataset split and sampling

Qasper is loaded from the public Hugging Face dataset repository. The current repository still contains a Python loading script, which recent `datasets` releases do not execute. The preparation loader therefore obtains the official Hugging Face Parquet conversion, pins its conversion commit, and records both it and the source repository commit.

Sampling uses `random.Random(42)` at the paper level. Development uses 15 papers from `train`; the primary held-out evaluation uses all 281 papers in the official `validation` split. A separate 50-paper validation pilot supports quick iteration and is reported separately. All questions belonging to selected papers are retained. No paper IDs overlap. Results must not be described as Qasper test-set results.

## Paragraphs and evidence

Each nonempty source paragraph receives a stable parent ID encoding paper, section, and paragraph order (`paper_id:p<section>-<paragraph>`). The primary comparison uses token-aware child passages capped at 450 model tokens with 50-token overlap. Each child retains its parent paragraph ID; evidence is counted as retrieved when any child of a gold paragraph appears in the ranked list. This avoids counting one long annotated paragraph multiple times. Original paragraph retrieval is retained as a development-set ablation.

Every answer annotation is retained, including extractive spans, free-form answers, yes/no labels, unanswerable flags, evidence text, mapped evidence IDs, and unmapped evidence text. Evidence maps only when it equals a source paragraph after NFKC normalization, control-character cleanup, whitespace collapsing, and case folding. Unmapped evidence remains visible in prepared data and data-quality outputs. Figure/table captions and original section headings are exported to separate JSONL files for auditing; section headings with empty source bodies are retained. Neither captions nor headings are inserted into paragraph retrieval or scored as paragraph evidence.

## Retrieval metrics

Metrics are computed only for questions with at least one answerable annotation and at least one mapped evidence item. Evidence Recall@K and Complete Evidence Coverage@K are calculated for each valid annotator evidence set; the best alternative set is used for the question. This avoids requiring the union of distinct annotators' evidence. MRR@K and Hit Rate@K consider the union of mapped relevant paragraphs across answerable annotations. Unanswerable and unmapped-only questions are not counted as retrieval misses.

## Retrieval systems

BM25 uses the same case-folded alphanumeric tokenization for queries and passage text. Dense retrieval uses normalized Sentence Transformer vectors and cosine similarity in a persistent ChromaDB collection; the Sentence-BERT embedding approach is described by [Reimers and Gurevych (2019)](https://arxiv.org/abs/1908.10084). The embedding model is `sentence-transformers/multi-qa-MiniLM-L6-cos-v1` at revision `b207367332321f8e44f96e224ef15bc607f4dbf0`. Hybrid retrieval applies Reciprocal Rank Fusion [Cormack et al. (2009)](https://doi.org/10.1145/1571941.1572114) to the top-20 dense and BM25 ranks with `sum(1/(60 + rank))`. The Cross-Encoder (`cross-encoder/ms-marco-MiniLM-L6-v2`, revision `233902d25c440f23af6f7d6e94d2946bac0bee0a`) sees only the hybrid candidates and reorders them before final K=5 evaluation, following the passage reranking setup described by [Nogueira and Cho (2019)](https://arxiv.org/abs/1901.04085). Runs used the CPU device.

## Statistical analysis

The full-validation comparison reports per-question metrics and macro means on the same 888 eligible questions across all methods and 276 paper clusters. Percentile 95% confidence intervals use 2,000 bootstrap resamples of papers (seed 42), preserving within-paper question clusters. Paired comparisons resample each paper's per-question metric differences. The separate 50-paper pilot uses the same bootstrap procedure but has fewer clusters. Neither interval addresses uncertainty from changes in benchmark annotation or generalization beyond the validation split.

The top-K and chunking ablations use the 15-paper development subset (36 eligible questions). Results are descriptive and are not used to tune or select the held-out evaluation results. Question-type summaries are non-exclusive: questions with more than one answer type can contribute to multiple groups. Mixed answerability is a separate descriptive group.

## Reproducibility and boundaries

Dataset source revision `fdc9d8214fbab5dd782958601db4d678e6934a54` and Parquet conversion revision `06806e4608976fc2fac0a090ac425d5b2b29caf4` are explicit defaults in the preparation pipeline. Sample IDs, fingerprints, model revisions, parameters, machine Python version, metrics, latency, and predictions are saved in local run outputs. New experiment configurations record installed versions of the dataset, numeric, lexical, dense-retrieval, vector-store, transformer, and scikit-learn packages (optional packages absent from an environment are recorded as null). The original reported runs used Python 3.13.16; isolated Python 3.11.9 reruns now cover full validation, the 50-paper pilot, K=20 candidates, bootstrap statistics, error analysis, and development chunking/Top-K ablations. `scripts/compare_runtime_outputs.py` compares question sets, ranked paragraph and chunk IDs, retrieved text, scores, per-question metrics, configuration pins, and ablation rows; its machine-readable report is saved at `results/experiments/python311_runtime_parity.json`. The historical pilot Hybrid + reranker K=20 directory contains predictions but no reference config or metric CSV, so those original-file metadata checks are marked unavailable. A separate Python 3.13.16 reconstruction at `results/experiments/python313_reconstructed/pilot/candidates20/hybrid_reranked/` now supplies an independently recorded config and per-question metrics; its predictions match the historical file and Python 3.11.9 rerun, while its metric rows and protocol pins match the Python 3.11.9 run. This later reconstruction does not alter or claim provenance for the older artifact. Latency is retained per run because it varies with the host and cache state. Remote CI has not been run. No LLM generation is simulated; it remains separate pending a configured key and cost authorization.
